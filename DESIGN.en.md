# Design Principles and Maintenance Boundaries

## Repository Role and Capability Boundaries

`qatlib-tools` serves as shared engineering infrastructure and a maintenance handbook across multiple Lean 4 formalization projects, not as a thin wrapper layer around single-step command-line tools. Whenever a routine operation can be cleanly accomplished with a native `git`, `gh`, `tea`, or `gt` command—or a single direct hosting-platform API call—both the documentation and the implementation direct users straight to the official tools. Logic belongs in this repository as a shared capability only when multiple repositories repeatedly encounter the same class of cross-platform behavioral discrepancies, need to align verification evidence scattered across disparate interfaces to the exact same commit, or must enforce remote branch state checks before concurrent writes. Before introducing or modifying any public interface, verify real cross-repository reuse scenarios and existing consumer invocation patterns so that each interface retains a single responsibility and predictable behavior.

As a foundational shared repository, all code, tests, and documentation here remain general-purpose and project-neutral: implementations, test fixtures, and examples never hardcode downstream project names, directory layouts, problem-card schemas, approval state machines, or machine topologies. Dependencies flow strictly in one direction—downstream repositories pin specific versions of this repository and define project-specific policies in their own documentation and workflows, rather than this repository coupling back to individual consuming projects. When a project directory is ambiguous and the target cannot be uniquely determined from standard configuration files (such as `lakefile.toml` or `lake-manifest.json`), tools must fail fast with a clear error and require the caller to specify the target explicitly, rather than falling back on guesswork.

## Local Environment, Managed Execution, and Safe Cleanup

User-level configuration, static lexical indexes, and runtime state generated by the tools live under `${QATLIB_HOME:-~/.qatlib}` by default (relocating automatically when `QATLIB_HOME` is set); private databases, cache files, and temporary state are never written inside indexed or managed Git source worktrees. When directory conventions evolve, tools preserve backward-compatible reads or emit clear guidance for legacy environment variables, and never silently relocate build-pool ledgers or lock files in the background while concurrent processes are actively using them. Lake's own artifact caches, authentication settings for upstream CLI tools, and per-project worktree directories continue to follow their respective native conventions. Credentials, secrets, and personal machine-local paths must never be committed to the repository or echoed in plaintext to terminal output or logs; Python packages must always be installed via isolated virtual environments, `uv tool`, or `pipx`, and never written directly into the system interpreter.

When compiling Lean modules or running heavy external commands, processes must execute within bounded resource and lifecycle controls. During admission control, tools account for both available host headroom and visible limits across every level of the cgroup hierarchy, reserve a system safety buffer, and acquire leases from the machine-local shared resource pool according to the actual `jobs × lean_threads` product and memory budget; if the effective limits of the current environment cannot be reliably verified, managed entry points must refuse execution outright rather than silently falling back to unbounded execution. Parallel worktrees each maintain an independent `.lake` directory, sharing read-only build artifacts solely through a content-addressed cache and never sharing writable build directories across worktrees. On task cancellation or timeout, cleanup terminates only process groups, descendant processes, or transient control groups provably owned by the current task (such as Linux parent-death signal guards paired with subreaper adoption, systemd scopes, or Windows Job Objects). Tools never indiscriminately kill processes by name (such as `lean` or `lake`) on shared machines, and always preserve exact exit codes and timeout statuses.

Every cleanup operation involving worktrees, derived caches, or historical directories must preview target paths, Git ownership, unpushed commits, untracked or ignored local files, open pull requests, and resident processes before execution. Strictly within explicitly authorized scope, tools automatically reclaim only stale worktrees verified to be clean, idle, and already merged into the mainline, pruning stale `git worktree` registrations after moving the directories to the trash; any directory with unpreserved changes, an associated in-flight branch, or uncertain ownership is left intact and summarized for human review, without spending compute to speculatively rebuild temporary drafts. File and directory cleanup uniformly moves items into the system trash and verifies the receipt, never falling back to `rm`, `git clean`, or other permanent deletion methods.

## Collaboration Verification, Documentation Layering, and Change Protection

GitHub serves as the single authoritative source for collaboration in this repository. When verifying continuous integration status, tools align the actual conclusions of applicable workflows and individual jobs against the pull request's exact current `head` commit; conditionally skipped jobs (`skipped`), jobs that have not yet run, missing records, and infrastructure failures are never treated as passing. Merging pull requests and deleting remote branches must bind to the reviewed expected commit hash (while also checking the default branch and branch-protection rules before deleting a branch), preventing commits newly pushed after review from being silently absorbed or lost. Routine commits preserve the original human author and committer identities, run Git hooks normally, and add no AI attribution or tracking trailers; creating version tags, publishing releases, or uploading shared artifacts protected by write credentials requires separate, explicit authorization.

Repository documentation is organized in layers by audience and purpose: the root `README.md` / `README.en.md` and the online documentation site are written for human readers, explaining tool responsibilities, installation methods, and core engineering mechanisms in clear, natural prose; topic guides under `docs/` distill build caching, runner resource isolation, documentation and bibliography search, dual-platform collaboration verification, and cross-repository promotion into reusable, project-agnostic reference material (packaged for offline access via `qatlib-env docs` and built from the same source as the online site), while transient per-change logs stay in commit and issue history; exact command options, output fields, and preconditions are maintained canonically in `--help` and the test suite.

In `DESIGN.md`, the design-principles block delimited by standalone `<!-- human-contract:start -->` and `<!-- human-contract:end -->` lines, together with its companion digest manifest `docs/design/human-contracts.sha256`, is governed by change-verification checks and code-owner protection. Any pull request that modifies the protected block body, its start or end markers, or the digest manifest must first be opened as a draft presenting the full candidate text for maintainer review; only after approval may the digest hash be updated, the pull request marked ready for review, and the change merged under standard checks.
